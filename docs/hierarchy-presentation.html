Node-formula roll-up

Sensors are plain raw values — no formula, no per-sensor factor. A sensor knows which energy type it measures, whether another sensor's reading already covers it, and which way energy flows through it. Hierarchy nodes carry formulas that declare an (energy type, purpose) output and combine descendant sensors with coefficients. Pick an energy type and a purpose to watch the same tree answer a different question.

What changed: the formula moved off the sensors and onto the nodes — and the one mis-named axis split into two. Energy type (energitype) is what the sensor physically measures; it stays on the sensor. Purpose (formål) is what the energy is spent on; the node declares it, because the same sensor's kWh can be space heating here and DHW there. There is no “metric” axis: CO₂ and cost are derived from (energy_type, purpose) at read time, so the demo's old per-sensor emission factor is gone.
Terms are weighted Every term is reference × coefficient. Include = 1, subtract = −1, apportion = 0.28, convert = 10.45. Purely linear, so it commutes with hour/day bucketing and the roll-up keeps its one-pass shape.
Overrides only A formula lists only what differs from the default. Any sensor nobody mentions still counts at weight 1 — so attaching a sensor always moves the numbers and nothing is silently dropped.
The tree is the company's own Each company defines its own node types. This one runs property → building → area → meter; another might run field → array → sensor. Sensors hang off whatever node type that company uses, and formulas work the same either way — nothing here assumes a fixed shape.
Overlap is a fact, not a formula A sensor records which other reading already includes it — below, an accumulating channel and its three phase channels, all registers on one device and so all on one node. A covered sensor counts 0 wherever the covering one is also present, and 1 where it is not (a tenant submeter on its own area still shows that tenant's use, while the building counts it once via the main). Double counting stays structurally impossible instead of depending on someone remembering an override.
Direction is a fact too Import and export are separate sensors — two registers on one device — so the minus sign has to live somewhere. It lives on the export sensor (flow: out), not in a node formula: said once, correct at every level above. Neither fact can be read off the channel, so both are entered at onboarding.
Total & unallocated total is the net energy across the node's boundary: Σ in − Σ out. Fully metered that is consumption; without a production sensor it is the net grid position. unallocated = total − claimed, so partial instrumentation shows up as a number instead of disappearing.
Claims propagate up A purpose claimed on an area is claimed for its building, property and company too — purpose series roll up the tree exactly like total does. One sensor may feed many purposes, but all of its claims are declared on one node, and its coefficients for a given energy type sum to at most 1.
Derived rows When the declared output energy type differs from the sensors' — gas m³ × brændværdi × virkningsgrad, or el × COP — the row is derived. It is delivered energy, not metered consumption, so it never folds into any total.
Straight from Energihåndbogen Bimåler: DHW is metered, space heating = total − DHW. GUF/GAF: with no submeter, the degree-day-independent part is a standard 28 % of annual heat. Both are just weighted terms.

Domain Model

Node Hierarchy (HN0–HN9)

Rooted forest with up to 10 schema-defined levels — homogeneous nodes, per-tenant semantics

Tree Constraints

  • Every node has at most one parent (forest)
  • No cycles — acyclic
  • Up to 10 levels: HN0 (root) … HN9
  • HN0 = global root, HN1 = partner, HN2 = company; HN3–HN9 are schema-defined per company
  • Sensors carry the path of their owning node

Design Criteria

Key Design Decisions

Core principles governing the pipeline architecture

Append-Only / Event-Sourced

No updates or deletes. Corrections are new events with later created. Consumers use MAX(created).

Tombstone Deletion

Logical deletes via sentinel -1111111. Preserves audit trail.

Counter Reset Isolation

Negative delta → ANOMALY + new baseline. One point lost — absorbed by interpolation.

Two-Stage Filtering

A: Processor — reject corrupt payloads.
B: Temporal — 1h watermark + 6h buffer.

Bitemporal Option

active_from column (default = ingested_time). Backdate for retro hierarchy corrections.

Homogeneous Nodes

All hierarchy nodes share same entity. Differ only by metadata variant.

Streaming-First

Flink for real-time. Glue only for late arrivals (>6h) and backfills.

Manual via Pipeline

Manual readings enter via CSV/HTTPS — same pipeline, not a side-channel.

No Retro Re-enrichment

Historical data = historical truth. Bitemporal model enables override if needed.

Pipeline Architecture

Two branches from a shared parsed stream

Design Principle

Append-Only Correction Pattern

How logical_meter_data handles corrections without updates or deletes

Core Rule

The enriched Iceberg table is append-only. The same (logical_id, timestamp) pair may appear multiple times. Each append carries a newer ingested_time.

Consumers must query: MAX(ingested_time) per (logical_id, timestamp)

Three Correction Paths

1
Timer correction (<1h) — out-of-order record arrives, event-time timer re-emits corrected deltas with newer ingested_time
2
Late buffer hit (1–6h) — predecessor still in retention buffer, delta computed and appended
3
Glue recompute (>6h) — batch job reads raw_data, recomputes deltas, appends with current ingested_time

Why not upsert? Iceberg on S3 Tables is append-only for throughput. The correction pattern avoids expensive merge-on-read. Queries use ROW_NUMBER() OVER (PARTITION BY logical_id, timestamp ORDER BY ingested_time DESC) to pick the latest version.

Happy Path

1. Normal In-Order Delivery

Messages arrive in timestamp order with minimal delay

1
Kinesis delivers JSON payload
2
Payload Processor routes to device handler → SensorRecord
3
Raw branch writes to raw_data
4
Enrichment resolves identity + hierarchy
5
Gauge: pass through immediately
Counter: buffer → find predecessor → emit delta
6
Written to logical_meter_data at checkpoint

Consumer sees

One row per reading, correct delta/value. Data appears within ~5 min (checkpoint interval).

Handled In-Stream

2. Slightly Out-of-Order (<1h)

Messages arrive out of order but within the watermark window

1
T2 arrives first → buffered (baseline, no delta)
2
T1 arrives (earlier ts) → buffer sorts to [T1, T2]
3
T3 arrives → emitFromBuffer finds T2 predecessor, emits Δ(T3)
4
Watermark passes T1 → timer fires → emits Δ(T2)

Consumer sees

All deltas correct. Emission order differs from event-time order, but consumers query by (logical_id, timestamp).

Baseline

3. First Record for a New Meter

No previous value to compute a delta against

Counter Meters

  • First record has no predecessor → stored as baseline
  • No output, no error — by design
  • Second record produces the first delta
  • lastEmittedTs stays at Long.MinValue

Gauge Meters

  • Pass through immediately — no delta needed
  • Raw value is the final value

Error outputs

None. The "lost" first counter reading is the cost of delta computation — you need two points to compute a difference.

Dead Letter

4. Meter Identity Not Found

daqId has no mapping in DynamoDB or broadcast state

Common Causes

  • Meter recently installed, mapping not yet created
  • Typo in device configuration
  • Bootstrap scan failed & CDC hasn't caught up

Path

  • Raw branch: written to raw_data (no identity needed)
  • Enrichment: lookup fails → DEAD_LETTER
  • Nothing written to logical_meter_data

Recovery

Add the mapping to DynamoDB. New records enrich immediately. Historical gap: auto-backfilled via DDB Stream → Lambda → Glue (see Scenario 15).

Parse Error

5. Malformed / Unparseable Message

Invalid JSON, unknown schematype, or missing required fields

Common Causes

  • Firmware bug sending corrupt payloads
  • Network corruption in transit
  • New device type without a matching processor
  • Encoding issues (wrong charset, truncated payload)

Impact

  • No record in either Iceberg table
  • Error stream provides audit trail
  • Data is irrecoverable unless Kinesis retention allows replay after the parser is fixed

Unique risk

Only scenario where raw data is also lost. All other errors preserve raw_data.

Anomaly

6. Negative Counter Delta

Cumulative value drops below previous reading

Common Causes

  • Counter rollover / meter replacement
  • Meter malfunction
  • Firmware reset, battery replacement
  • Retroactive correction from utility

Behavior

  • Delta suppressed (not emitted)
  • Routed to ANOMALY side output
  • Cumulative value is kept in buffer as new baseline
  • Next reading computes delta from the new baseline

Design choice

No auto-correction for rollovers. Is 1000→500 a rollover or a replacement? False positives corrupt analytics.

Handled In-Stream

7. Late Arrival Within Buffer (1–6h)

Past watermark, but predecessor still in the 6-hour retention buffer

Common Causes

  • Device offline, batch-uploads on reconnect
  • Gateway network outage
  • Kinesis shard iterator falling behind

Path

  • Written to raw_data
  • emitFromBuffer adds to buffer, finds predecessor (still retained)
  • Delta computed and emitted immediately
  • Timer fires instantly (watermark already past) — dedup via lastEmittedTs

Consumer sees

Correct delta, just delayed. No error output. Transparent to consumers.

Batch Recovery

8. Late Arrival Beyond Buffer (>6h)

Predecessor purged from buffer — triggers automatic batch recomputation

1
Record added to buffer, no predecessor found
2
lastEmittedTs > MinValue → not first record
3
Routed to LATE_ARRIVAL side output
4
Error Kinesis → Lambda trigger
5
Lambda groups by daq_id, computes time range
6
Starts Glue job: reads raw_data, joins DDB, LAG() deltas
7
Appends corrected rows with created=now()

Consumer sees

Initially nothing. After Glue job (~minutes), corrected records appear. MAX(created) query picks them up.

Complex

9. Massive Historical Backfill

Millions of records spanning months/years arrive in a short burst

What Happens

  • All records written to raw_data (handles any volume)
  • Most deltas computed via emitFromBuffer (immediate)
  • Watermark jumps rapidly → buffer purges aggressively
  • Records caught between purge waves → LATE_ARRIVAL

Operational Steps

  • Consider scaling Flink parallelism for large backfills
  • Run --daq_ids=* Glue recomputation after backfill to fill gaps
  • Iceberg compaction needed after many small checkpoint files

Consumer sees

Most data correct in-stream. Gaps filled by auto-triggered + manual Glue recomputation. Final result is complete.

At-Least-Once

10. Duplicate Messages

Kinesis delivers the same record twice, or device sends duplicate

Counter Meters

  • Buffer keyed by eventTs (millis)
  • Second record overwrites first — put() is idempotent for same key
  • If values identical: delta unchanged
  • If values differ (same ms, different reading): last-write-wins

Gauge Meters

  • Both copies pass through to logical_meter_data
  • Duplicate rows in output table
  • Consumers should use SELECT DISTINCT or dedup

Note

Exactly-once only within checkpoint boundaries. Kinesis replay after failure may cause limited duplicates for any meter type.

CDC Event

11. Meter Identity Changes Mid-Stream

Sensor moved to a different node or reassigned to a new logical meter

Path

  • DynamoDB update → CDC event via Kinesis
  • DdbStreamDeserializer produces MODIFY event
  • Broadcast state updated with new mapping
  • Subsequent records enriched with new hierarchy IDs

Semantics

  • No retroactive correction — by design
  • Historical records keep original enrichment
  • The meter was at Node A at that time

Edge case

DDB update + sensor record near-simultaneous: race on broadcast join. Both values "correct" at boundary — operationally negligible.

Dead Letter

12. Meter Identity Deleted

Device decommissioned — mapping removed from DynamoDB

Path

  • CDC REMOVE event updates broadcast state
  • All subsequent records for this daqId → DEAD_LETTER
  • Raw data continues accumulating

Recovery

  • If accidental: re-add mapping to DynamoDB
  • New records enrich immediately
  • Run Glue recomputation for the gap period

If intentional

Dead letters are expected. Monitor error stream for unexpected deletions vs. planned decommissions.

Checkpoint Recovery

13. Flink Job Restart

Code deploy, scaling, or failure triggers restart from checkpoint

What's Restored

  • readingBuffer MapState (counter history)
  • lastEmittedTs ValueState (dedup tracking)
  • Broadcast state (meter identity cache)
  • Kinesis consumer offsets

Fresh on Restart

  • bootstrapCache re-scanned from DynamoDB in open()

Possible duplicates

Records between last checkpoint and crash are re-read from Kinesis. Limited duplicates for the CP-to-failure window (~5 min max).

Idleness

14. Kinesis Source Idle

No sensor data for extended periods

Behavior

  • Watermark idleness: 24 hours
  • After timeout, partition stops blocking global watermark
  • Other partitions continue normally
  • Data resumes: partition reactivates

No errors

No data in = no data out. Expected behavior for offline devices.

Risk

If ALL partitions idle >24h then data bursts arrive, watermark jumps → legitimate records may trigger Scenario 8 (late arrival beyond buffer).

Auto Backfill

15. Backfill on New Meter Mapping

Meter sends data before its identity mapping exists in DynamoDB

Problem

  • Meter sends data before mapping exists
  • Records land in raw_data but not logical_meter_data
  • Adding the mapping only enriches new records
  • Historical gap between first data and mapping creation

Automatic Recovery

  • DDB Streams fires INSERT event on new mapping
  • backfill-trigger Lambda receives the event
  • Extracts daq_id from the new mapping
  • Uses DDB write timestamp as time_range_end cutoff
  • Starts Glue job for only that daq_id
  • Glue reads raw_data up to cutoff, enriches, writes to logical_meter_data

Zero Manual Intervention

Cutoff = DDB event time prevents overlap with Flink streaming. Duplicate check skips if Glue job already running for same daq_id.

Configuration

16. Timestamp Resampling

Optional per-meter timestamp rounding to fixed intervals (5, 15, or 60 min)

How It Works

  • Optional resample_minutes column (integer minutes) on meter-identity — populated by the ems_ocaml bridge
  • Absent or null → raw row written, resample_* columns NULL
  • ResampleFunction (replaces CounterDeltaFunction) holds one-reading lag per meter; emits one row per resample grid point when next reading arrives
  • Original timestamp & value preserved; resample_timestamp/resample_value/resample_method added

Counter Meters

  • For each resample window [B−step, B] overlapping (prev_ts, current_ts]: emit one row
  • resample_value = delta × overlap / total_period
  • Energy conservation: SUM(resample_value) per reading equals delta; consumers SUM per (logical_id, resample_timestamp) after dedup
  • Method: "time_proportional"

Gauge Meters

  • One row per resample grid point B in (prev_ts, current_ts]
  • Linear interpolation between (prev, current) evaluated at B
  • Method: "linear_interpolation"

Glue Parity Invariant

Late-recomputation Glue job applies identical bin formula + unit normalization — bit-for-bit same output as Flink for the same input.

Aggregation

Measurements Aggregate — Materialized View

Pre-aggregated counter consumption in DynamoDB, queryable by hierarchy path (added 2026-06)

Why

Dashboards need fast “consumption for node X over period P” without scanning Iceberg. A scheduled Glue job rolls logical_meter_data counters into a DynamoDB table, pre-summed per node / purpose / hour & day.

Key design

  • pk = "HN2#<company>" — partition per company
  • sk = "<full hierarchy path>#<purpose>#<gran>#<bucket>"
  • One item at every level (HN2…leaf) — any node total is an O(1) read
  • # vs | delimiter keeps a node's own rows before its descendants' — subtree & interval queries via begins_with / BETWEEN
  • Attributes: sum, count, min, max, last_value, last_ts, unit
  • TTL: hourly 90 days, daily 2 years

Population — hourly Glue

  • Window by resample_timestamp over the last N whole UTC days (--lookback_days, default 1) so whole buckets recompute
  • Newest ingested_time per (logical_id, resample_timestamp) — honours the append-only / event-sourced table, so restatements never double-count
  • Counters only (resample_method = 'time_proportional')
  • Explode each reading up its ancestor path → group by node/purpose/gran/bucket → PutItem overwrite (idempotent)

Example item

pk = HN2#10003
sk = HN2#10003|HN3#9|HN4#456#Energy#d#2026-06-07
sum=660.07  count=288  unit=Wh

Design Philosophy

Everything Is a Graph

A hierarchy is just a DAG — sensors are just leaf nodes

  • A hierarchy is a DAG — no special tree type needed
  • Nodes are typed but homogeneous — structure is metadata
  • Only the traversal mechanism is rigid
  • Everything else is per-company schema: allowed node types, edge cardinality, required metadata fields
  • Access = entry-point into the graph — users see only their sub-graph
  • Edges encode both structure and permissions
  • Sensors are leaf nodes — no special-casing
  • DynamoDB adjacency list → sub-millisecond traversals, no joins
Domain Model

Hierarchy Levels — hn0 to hn9

Hard-coded spine (hn0–hn2), schema-defined subtree (hn3+)

Fixed spine (hn0–hn2)

  • hn0 — singleton root, HN0#root
  • hn1 — business tenant (partner)
  • hn2 — company; carries the schema definition

Schema-defined subtree (hn3–hn9+)

  • Semantics are declared by the company schema
  • Different companies → completely different tree shapes
  • Level-skipping allowed if schema declares the edge
  • Sensors can attach at any schema-declared level

Node identity

  • Id format: HN<n>#<int>
  • Integer is unique within a level, not globally
  • Full identity = level + integer pair
  • Each level has its own monotonic counter
Access Control

User Types & Permissions

Permissions are structural — they follow the graph

Role Entry point Can do
Platform Admin hn0 (root) Full access — all partners, companies, users
Partner Admin hn1 Manage companies in their partner; create company admins
Company Admin hn2 Add/delete nodes, define schema, manage users
Write User hn3+ (configured) Edit metadata on accessible nodes — cannot restructure
Read User hn3+ (configured) Read-only view of nodes & measurements in sub-graph
Blocked — Node (and subtree) is invisible — e.g. restricted lab

Inheritance: permissions flow top-down from the entry-point node unless explicitly overridden on a specific node.

Field-level access (CEDAR rules) is possible but seems overkill at this point — graph-level permissions are sufficient for most cases.

Per-Company Schema

Schema — One Model, Many Shapes

Each hn2 company owns a schema that governs its entire subtree independently

Schema declares

  • Edges — allowed parent→child pairs with label, min/max cardinality
  • Metadata fields per level — typed, required or optional
  • Sensor levels — which levels may have sensors attached

Typical property management schema

hn2 → hn3 "property" (min:1)
hn2 → hn3 "group"
hn3 → hn4 "building"
hn4 → hn5 "floor"
hn5 → sensor

hn3 metadata:
  address: string, required
  lat: float, required
  lon: float, required

Typical industrial schema

hn2 → hn3 "site"
hn3 → hn4 "machine-room"
hn3 → sensor (skip!)

hn3 metadata:
  site_id: string, required
  capacity_kw: float

Conclusion

Key Takeaways

Simplicity through principled thinking — not through restriction

Graph-first model

  • Hierarchy = DAG; access = sub-graph entry-point
  • Sensors are leaf nodes — no special cases
  • One model covers all customer shapes
  • Per-company schema → zero cross-tenant bleed

Extensible by design

  • Add a new node type → update schema, no code change
  • New metadata field → schema update, validated at write
  • New company shape → new hn2 schema, independent

Performance & cost

  • DynamoDB adjacency list — sub-ms traversals, no joins
  • All Lambdas — no long-running servers
  • No synchronous call takes > a few seconds
  • Reports as async background jobs

Pipeline simplicity

  • One data hose — all sources, common error handling
  • Append-only, event-sourced — no UPDATE/DELETE
  • Data enrichment in Flink — never blocks user requests

Operations

  • 2–3 true microservices + a few helpers
  • Regional by design — deploy anywhere in minutes
  • All queries isolated — one user's report can't slow others
